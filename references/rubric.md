# Session 診斷準則

> 「糾正代理時先想哪一層」與「三支柱」取自 poteto（Lauren Tan）的演講：https://x.com/poteto/status/2102050467505430555 。這裡是非官方的整理與延伸，與本人無關；如有誤解，以原演講為準。

給診斷用 subagent 讀。目標：找出這次對話「哪裡卡住、為什麼、下次該修哪裡」，而不是給對話打分數。

## 一、找出糾正與介入點，以及沉默的失敗

逐輪讀完整份摘要（長檔分段讀，不可只讀開頭）。這一節分兩半，**兩半都要做**：第一半找「有人出手」的地方，第二半找「沒人出手、但可能出錯」的地方。

### 糾正與介入點

poteto 的起點是**使用者糾正或介入代理的那一刻**：每當你發現自己在糾正、介入代理，就從五層去想（見第二節）。所以最核心的一類是：

- 使用者糾正、重講、打斷、改方向、表達不滿（摘要標 ⚑ 的只是關鍵字提示，要自己判斷，也要找沒被標到的）

以下幾類是**本技能的延伸**，不是 poteto 原本的說法。它們沒有使用者出手，但同樣是代理偏離的跡象：

- Claude 自己承認做錯、撤回說法、同一件事重做
- 工具錯誤或被拒絕後，Claude 繞路、重試同一招、或假裝成功
- Claude 宣稱完成，但後面證明沒完成或沒驗證
- 花很多輪做使用者沒要的事，或問了不必要的問題

每個糾正與介入點要有**證據**：摘要中的輪次、時間與原文短引。沒有證據就不要列。報告裡標明每一點屬於「使用者糾正／介入」還是「延伸類」。

### 沉默的失敗

沒人糾正，不代表沒出錯；可能只是沒人去檢查。只看糾正點，會把「錯了但沒被發現」的對話判成沒問題。所以**不管有沒有糾正點，都要主動檢查**：

- **宣稱沒有證據**：Claude 說「完成」「測試通過」「已確認」「已修好」，但前後找不到對應的證據（測試輸出、實際打開的畫面、比對過的數字、讀過的檔案）。
- **會吞掉錯誤的指令寫法**：例如 `|| true`、`2>/dev/null`、`| tail`／`| head`（沒開 `pipefail` 時，前面指令失敗也不會被發現）、`set +e`、`except: pass`。要看結果有沒有因此被誤判成功；只是縮短輸出、而且另有確認的，不算。
- **資料被過濾、刪除、覆寫後，沒有印出前後筆數或抽樣**。
- **交代的步驟被悄悄省略或縮水**：例如「看 10 頁」只看了 2 頁、「每個檔案都改」只改了一部分，而使用者沒有追問。
- **失敗後照樣往下走**：測試或檢查失敗了，卻照樣提交、發布或宣稱完成。

**從一次回推全部**：只要找到一次沉默的失敗（或一次被使用者抓到的錯），就回頭搜尋整份摘要（必要時 grep 原始紀錄），看同樣的寫法或行為還出現過幾次。被抓到的往往只是其中一次。

沉默的失敗同樣要附輪次與原文短引，並寫明「為什麼判斷證據不足」。可能有合理解釋的（例如證據在被截斷的工具輸出裡），標「低信心」並說明。

**沒有糾正點時，結論要分兩種說法**，不能只寫「沒問題」：

- 「查過了，確實沒問題」：列出檢查了哪些宣稱、各自的證據在哪一輪。
- 「沒人糾正，但有 N 處宣稱沒有證據」：列出這 N 處。

這對應支柱一（第七節）：信任要建立在能證明的東西上，而不是「沒人抱怨」。

## 二、判斷根本原因：問題出在哪一層

依 poteto 的「糾正代理時先想哪一層」，對應到 Claude Code：

| 層 | Claude Code 裡是什麼 | 何時該修這層 |
|---|---|---|
| 1. 程式碼庫 | 專案程式碼、資料夾結構、既有寫法、範例檔 | Claude 照抄了壞範例；專案結構讓錯誤很容易發生 |
| 2. 靜態／自動檢查 | 測試、lint、型別檢查、hooks、`settings.json` 權限 | 同類錯誤可以被機器確定地偵測或阻擋 |
| 3. 規則 | CLAUDE.md、`~/.claude/rules/`、記憶檔、其他被載入的指示檔（如 AGENTS.md） | 需要判斷、無法機器檢查的偏好或流程 |
| 4. 技能 | `~/.claude/skills/`、專案的 `.claude/skills/`、外掛技能 | 特定任務需要一套做法或工具 |
| 5. 人工糾正 | 使用者在對話中親自提醒 | 只有這次特例才需要，否則應往前推 |

驗證與品質另見第七節「三支柱體檢」：這裡只判斷單一問題點的原因，第七節看整體該建什麼。

「程式碼庫」不只指程式碼。非寫程式的專案裡，它指專案的檔案結構、範本、既有成品與資料：Claude 一樣會照抄眼前看到的東西。

每個糾正與介入點、每個沉默的失敗，都選一個**根本原因**：

- `規則缺漏`：沒有任何指示涵蓋這件事
- `規則未遵守`：指示存在（引用檔案與段落）卻沒被照做——再判斷是指示太長被淹沒、措辭模糊、還是被其他指示蓋過
- `規則衝突`：兩份指示互相矛盾，或指示與使用者當下要求矛盾
- `規則過時`：指示提到的檔案、指令、工具已不存在
- `壞範例擴散`：Claude 照抄了專案裡既有的壞寫法
- `缺驗證`：Claude 沒有、或沒用可驗證成果的方法（支柱一）
- `缺品質做法`：結果對了，但做法不符使用者期待——冗長、自己重造現成工具、不符風格、難維護（支柱二）
- `模型判斷`：資訊都在、指示也清楚，仍然判斷錯（不要把所有問題都推給這項）
- `提示不足`：見第三節

然後建議**修在哪一層**：能往前推就往前推（能用 hook 或測試擋的，不要只寫進 CLAUDE.md）。

## 三、使用者提示分析

公平看待，不責怪使用者。分辨「提示真的缺資訊」和「Claude 本該自己查到或合理推斷」。常見情況：

- 目標或成品不清楚（要摘要還是全文？要改檔還是只要建議？）
- 缺少驗收條件（怎樣才算完成）
- 指代不明（「這個」「那邊」「照之前那樣」）而前文有多種可能
- 一句話塞多個互相牽動的要求，沒有排序
- 中途改方向但沒說要放棄哪些已做的部分
- 當下要求與 CLAUDE.md 規則衝突，卻沒說明哪個優先
- 缺少 Claude 無法得知的背景（帳號、偏好、先前討論）

每一點附原文引用，並給一個**改寫範例**：同一個要求，下次怎麼說會更順。如果某個提示其實很清楚、是 Claude 沒做好，要直接說清楚。

## 四、指示檔本身的健康檢查

讀過的每一份指示檔，檢查：

- 重複：同樣內容在多份檔案裡（每次都佔用 Claude 的閱讀空間，而且日後改一份就會不一致）
- 矛盾：兩處規則互相衝突
- 失效：提到已不存在的路徑、指令、工具（實際用 ls 或讀檔確認）
- 不可執行：寫成規則但其實應該由 hook 或測試強制的東西
- 太長或太散：重要規則被埋在大量次要內容裡

只報告與本次發現的問題點有關、或明顯影響所有對話的問題。

## 五、輸出格式

用使用者的語言（預設繁體中文）、白話，技術詞第一次出現加半句解釋。依序：

1. **一句話結論**：這次對話最主要卡在哪裡。沒有糾正點時，依第一節用「查過了，確實沒問題」或「沒人糾正，但有 N 處宣稱沒有證據」其中一種說法。
2. **糾正與介入點清單**（最嚴重在前）：每點包含
   - 類型：使用者糾正／介入，或延伸類（見第一節）
   - 發生了什麼（使用者角度）＋證據（輪次、時間、原文短引）
   - 根本原因（第二節分類）
   - 建議修在哪一層、哪個檔案、改成什麼（給具體文字或 hook 草稿）
   - 範圍：全域或專案（依第六節），以及對其他類型專案的影響
   - 信心：高／中／低，以及為什麼
3. **沉默的失敗**：依第一節的檢查項目逐項回報。每項寫出宣稱或寫法的原文、所在輪次、為什麼判斷證據不足、同樣情況共出現幾次、根本原因與建議修在哪一層。某項查過沒有發現，也寫「查過，沒有發現」。
4. **三支柱體檢**：依第七節的表格，每根支柱一列。
5. **提示分析**：值得改的提示，附改寫範例；沒有就說沒有。
6. **指示檔健康檢查**：發現的重複、矛盾、失效項目，附檔案路徑與行號。
7. **做得好的地方**：值得保留的流程（簡短）。
8. **限制**：沒讀到的東西（被截斷的內容、無法開啟的檔案、subagent 紀錄是否有讀）。

不要修改任何檔案。所有修改都是建議，由使用者決定。

## 六、影響範圍：全域還是專案

使用者的專案用途可能各不相同（寫程式、資料庫、資料處理、寫文件……）。全域設定（`~/.claude/` 底下，以及其他使用者層的指示檔）會影響每一個專案；專案設定只影響該專案。**預設放專案層**，只有符合下列條件之一才建議全域：

- **關於使用者這個人，而且與專案類型無關**：溝通方式、語言、決策時要怎麼問、不可逆操作前先確認。
- **觸發條件很窄的安全檢查**：例如 hook 只在「同一行指令同時有 `pytest` 和 `git commit`」時才動作；用不到它的專案永遠不會碰到。要寫出觸發條件，並說明為什麼其他專案不會被誤擋。
- **純整理、不改變行為**：例如刪掉重複的指示檔內容；要說明內容前後相同。

下列情況放專案層：

- 與某類工作綁在一起的流程：資料批次、測試方式、檔案結構、該用的工具。
- 只在這一個專案、這幾次對話觀察到的問題（還不能確定是跨專案的模式）。
- 專案特有的環境細節（例如某台機器沒有某個指令），除非使用者的所有專案都在同一台機器上，而且都會用到它。

每條建議寫出：放哪個檔案、屬於全域還是專案、對其他類型專案（寫程式、資料、寫文件）會有什麼影響。若建議全域卻只看過一次，就降為「低信心」，並建議先放專案層試用。

全域指示檔若已經混了只對特定類型專案有用的規則，也在第四節列出，並建議搬到對應的專案。

## 七、三支柱體檢：除了抓錯，也說該建什麼

poteto 建立信任的三根支柱。糾正點與沉默的失敗回答「哪裡出錯」，這一節回答「這個專案還缺哪根支柱、下一步建什麼」。每根支柱依這次對話的證據評為**有／部分／沒有**。建議要具體到能直接動手：寫出名稱、放哪、裡面有什麼、怎麼用；範圍依第六節，通常是專案層。

### 支柱一：驗證——代理能不能自己證明做對了

poteto 的驗證技能有兩半：**操作工具**（固定的指令，能跑出真實結果並收集證據）加上**地圖**（這個專案有什麼、東西在哪、怎麼到達）。檢查：

- 成果能不能用可重複的方式驗證？還是每次都臨時寫一段腳本、每次寫得不一樣？
- 驗證有沒有碰到真實的東西（實際執行、開頁面、對照原始資料），還是只看「沒有報錯」或看摘要數字？
- 使用者是否得親自去看才知道對不對？每一次「你有沒有確認過」都是這根支柱的缺口。
- Claude 是否因為不知道東西在哪、哪份是最新的，而猜錯或找錯？這是缺地圖。

建議的形式：把反覆出現的驗證寫成專案技能裡的固定腳本，並說明輸入、輸出與判斷標準。專案也要有一份持續更新的「地圖」檔，說明有哪些資料或功能、現況如何、放在哪；要寫出由誰、在什麼時候更新，否則它會過時。依專案類型舉例：

- 寫程式：啟動 app 並擷取畫面或效能紀錄的指令、端到端測試
- 資料處理：抽樣比對原始檔的腳本、每批次的前後筆數與異常樣本報告
- 寫文件或網頁：實際開啟頁面截圖、檢查連結與引用來源

### 支柱二：品質技能——代理有沒有照使用者期待的方式做

驗證只回答「對不對」，這根支柱回答「好不好」。檢查：

- 使用者有沒有糾正「做法」而不是「結果」？例如「怎麼不先找現成工具」「太複雜了」「不要這樣寫」。
- 同一類任務，Claude 每次做法不一樣，還是有固定的好流程？
- 相關的技能存在但沒被觸發（說明寫得不夠好認），還是根本沒有？

建議的形式：把使用者的偏好做法寫成技能——寫出技能名稱、什麼情況下會用到（就是技能說明裡的觸發描述）、步驟要點，以及一個好的範例。已有技能但沒被觸發，就建議改它的說明，不要另寫一個。

### 支柱三：對代理友善的結構——預設就會做對

也就是第二節的五層。這一節看整體：這個專案有沒有「唯一一條鋪好的路」？壞範例、過時的檔案、重複的版本是不是還留在 Claude 看得到的地方？有沒有一再發生、應該從規則層往前推到自動檢查層的錯？

### 輸出表格

| 支柱 | 狀態 | 證據（輪次、原文短引） | 下一步建什麼 | 範圍 |
|---|---|---|---|---|
| 一、驗證 | 有／部分／沒有 | … | 具體名稱、位置、內容 | 全域／專案 |
| 二、品質技能 | … | … | … | … |
| 三、友善結構 | … | … | … | … |

沒有證據就寫「這次對話看不出來」，不要硬評。
